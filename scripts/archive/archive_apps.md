# 统一归档应用

## 用途与影响

入口：[archive_apps.sh](./archive_apps.sh)。

脚本接收一个或多个应用目录名，从活动应用清单和归档映射中读取原构建路径及固定资产名，不按目录名猜测 Release 附件。适用于本仓库已登记的、具有固定 `.AppImage` 资产名的应用；不能直接用于 RunImage、Termux、未登记项目或其他仓库布局。

默认只预览本地归档计划，不修改应用文件、不提交推送，也不访问 GitHub。显式传入 `--yes` 后，脚本按顺序执行：

1. 保留完整应用目录、原脚本和文件权限，移入 `archive/<原目录>/`；在归档 README 顶部追加日期、原因、备注及恢复入口，保留原有记录并调整相对链接。
2. 移除活动清单、手动构建选项及必要的专属 Job，更新归档映射、归档索引和相关文档引用。其余工作流的 YAML 语义必须保持不变；发现无法处理的引用时停止。
3. 仅暂存本次归档涉及的路径，检查暂存差异，创建一个中文提交并推送到 `main`。提交身份使用当前 GitHub 账户的公开用户名和 noreply 邮箱，不修改本机 Git 身份配置。
4. 逐个调用现有 [附件删除入口](../release/delete_asset.md)，精确删除 `latest` 中的对应附件；再调用现有 [独立归档清理入口](../../.github/scripts/prune_archived_versions.sh)，按写锁机制清理符合条件的归档版本条目。
5. 重新完整读取附件分页，确认所选附件不存在；核对 `software_versions.json` 的摘要和内容、对应版本条目及工作区状态后，才报告完成。

版本清理复用现有机制，会核对归档映射中所有符合条件的条目，并非仅处理本次传入的目录；不符合条件的条目保持原样。附件删除只针对本次所选应用的固定资产名，不删除整个 Release、Tag 或其他附件。

脚本不安装软件、不修改系统配置，也不主动触发或等待 Actions。推送仍会按仓库已有条件触发工作流；已有独立清理可能并发运行，版本清单写入继续使用共享写锁。

## 运行条件

- 查看帮助需要 Bash 和 Python 3；预览还需要 Git 和 PyYAML。实际执行另需 `gh`、`jq`、`timeout`、`sha256sum` 及常用 Linux 命令。脚本只检查依赖，不自动安装。
- `gh` 需支持 `gh api --paginate --slurp`，Git 需支持通过标准输入读取 NUL 分隔的路径清单。附件分页数据由标准输出读取，不作为大段命令参数传递。
- 脚本必须位于目标仓库的 `scripts/archive/`。预览和执行都要求工作区没有未提交或未跟踪文件；待移动目录也不能含被 Git 忽略的文件。脚本不会替其他修改做暂存或提交。
- 实际执行必须位于 `main`，本地 HEAD 与远端 `main` 一致，且 `origin` 对应显式填写的 GitHub.com 仓库；不会自动拉取、重置或强制推送。
- 实际执行需要已有的 `gh` 认证、Git 推送认证、向 `main` 推送的权限及 Release 写权限。浏览器登录不能代替命令行认证。认证信息只在运行时读取，不作为文档或示例提交。
- `latest` Release、活动清单、归档索引、归档映射及两个现有清理入口必须完整。映射冲突、资产名不唯一、目录异常或工作流结构不符时停止，不扩大处理范围。

执行前先完整阅读应用 README，确认成功基线、尚未解决的错误和恢复待办。脚本不会读取构建日志、补写故障证据、修复程序或扩大实机验证范围；缺失记录应先另行补全并提交。归档要求见 [归档与恢复说明](../../archive/README.md)。

## 使用方法

在目标仓库根目录的 Linux 终端执行。以下占位符均须按本次已经核实、允许公开的内容替换；一个目录名对应一个参数，不填写完整路径或构建脚本路径。

```bash
# 查看参数说明；此操作不查询 GitHub，也不执行归档。
bash scripts/archive/archive_apps.sh --help
```

先预览同一批应用及其公开备注：

```bash
# 预览两个应用的完整归档计划，不修改文件或发布内容。
bash scripts/archive/archive_apps.sh --dry-run --reason "<公开归档原因>" --note "<应用目录>=<公开故障记录与恢复待办>" "<应用目录>" "<另一应用目录>"
```

`--dry-run` 可省略，默认行为相同。按实际数量填写目录；没有备注时省略 `--note`。多个项目需要不同备注时，分别重复该参数。预览只检查本地计划，不表示远端权限、附件状态或真实删除已经验证。

以下命令会移动目录、修改登记和文档、提交推送，并删除所选应用在 `latest` 中的附件及清理符合条件的归档版本条目。确认这些影响均已获得授权后，保留预览时的目录、原因和备注，显式执行：

```bash
# 按已核实的仓库和预览内容执行完整归档及发布清理。
bash scripts/archive/archive_apps.sh --repo "<所有者>/<仓库>" --reason "<公开归档原因>" --note "<应用目录>=<公开故障记录与恢复待办>" --yes "<应用目录>" "<另一应用目录>"
```

统一入口已经调用附件删除和版本清理，不需要再对同一批项目手工重复整套操作。只有独立删除某个附件时，才单独使用 [delete_asset.sh](../release/delete_asset.md)。

## 参数说明

| 参数 | 要求 |
| --- | --- |
| 应用目录 | 至少一个，可填写多个；必须是清单中的单层目录名，不能重复，不能使用路径或通配符 |
| `--repo OWNER/REPO` | 实际执行时必填；只接受 GitHub.com 仓库，并核对 `origin`，不自动从当前目录推断删除目标 |
| `--reason` | 可选，默认“暂停维护，按需恢复”；同批新归档项目使用相同原因，内容会写入公共文档 |
| `--note 目录=公开说明` | 可重复；目录必须属于本次选择且不能重复备注。写入本次新归档项目的 README，可记录已核实错误、证据链接、实际验证范围及恢复待办 |
| `--dry-run` | 只预览，与默认模式相同；不能和 `--yes` 同用 |
| `--yes` | 明确执行完整归档、提交推送和发布清理；缺少时始终只预览 |
| `--help`、`-h` | 显示帮助后退出，不检查 Git 或 PyYAML，不访问 GitHub |

归档日期使用执行时的 UTC 日期。当前脚本统一将“替代”登记为“无”，不自动判断替代软件；存在其他替代要求时先核对处理范围，不把脚本当作可适配任意归档格式的工具。已经归档的目录不会因再次传入原因或备注而重写原有 README。

## 执行结果

正常预览或完整执行成功时返回 `0`；参数解析错误返回 `2`，其他校验或执行失败返回非零。预览、提交推送成功、附件删除成功和完整归档完成是不同阶段，不能互相代替。

- 预检查失败时停止，不继续修改或清理；文件已经移动、暂存或提交后失败时，可能保留部分本地结果。脚本不自动回滚、强制同步或掩盖失败，应先核对实际文件、暂存区、提交和远端状态。
- 归档提交已经成功推送，但发布清理失败时，确认工作区干净、本地与远端 `main` 一致后，可使用相同目录及 `--repo`、`--yes` 续跑。现有归档登记完整时只复查和清理，不再次迁移目录或生成重复提交。提交或推送阶段失败不属于这种情况，不能盲目重复运行。
- 附件本来不存在时，由现有删除入口完整查询后报告无需删除。查询失败、Release 变化、同名附件重复、摘要异常或目标条目仍存在，都不能当作完成。
- 完成后应能核对归档目录、活动入口、归档映射、指定附件及版本条目。结果只说明归档流程，不表示构建通过或实机功能验收；恢复仍按 [重新启用说明](../../archive/README.md#重新启用)处理。

当前脚本已在临时测试仓库配合模拟 GitHub 响应完成离线检查，覆盖默认预览、错误参数、大附件分页、原脚本及权限保留、完整流程、重复执行和删除失败后的续跑。该检查没有对真实应用执行归档或删除 Release 附件。
